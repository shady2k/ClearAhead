# Контракт отрисовки и типы путевых конструкций

Дата: 2026-08-09. Редакция 5 (после четырёх заходов состязательного ревью).
Предшественники: `2026-08-08-map-format-design.md` (§7, §8, §12, §13),
`2026-08-08-vertical-slice-design.md`, решение сессии `ClearAhead-amh`.

---

## 1. Что решается и почему сейчас

Клиент на Godot берёт из контракта осевые линии и **достраивает остальное сам**:
колея 1435 мм, шаг шпал 0.6 м, шпала 2.5 м поперёк, балласт ±1.75 м, ширина
платформы 3.0 м и её отступ 1.75 м — всё это константы в
`client/scripts/world.gd`.

Часть из них — стиль, и там им место. Часть — авторитетные факты о станции, и
тогда их выдумывание клиентом означает, что второй рендерер выдумает свои. За
один день разошлись контракт с клиентом (`ClearAhead-reb`), валидация с
реальностью (`ClearAhead-ynk`) и спека с фактическим клиентом (Godot против
записанного SVG + DOM); это не гипотетический риск.

Решение о рендерере объявлено обратимым (`amh` п.4). **Обратимость — свойство,
которое поддерживают, а не наблюдают.**

Не решается здесь: выбор движка (Godot остаётся), клотоида и возвышение
(отложены §12, потребителя нет), полная генерация карт (отклонена
`deferred-decisions.md:144-176`).

## 2. Граница ответственности — по авторитетности

`map-format-design.md:215` уже отверг слишком буквальную границу «о чём
рассуждает сим — топология, что рисуется — контент». Первая редакция настоящей
спеки провела свою, столь же буквальную: «всё метрическое — сервер». Она
неверна и заменяется.

> **Сервер и привязанные к ревизии ресурсы владеют авторитетными фактами:**
> идентичностью, связностью, референсными осями, типами конструкций и
> каноническими адресами значимых особенностей.
> **Клиент владеет изображением этих фактов:** тесселяцией, уровнями
> детализации, материалами, экранными толщинами, скруглениями и стыковкой.

Единица измерения владельца не определяет. Проверка — вопрос «это факт о
станции или способ её показать»:

| Величина | Владелец | Почему |
|---|---|---|
| ширина платформы | сервер | факт о станции; по ней ходят люди |
| шаг шпал | сервер | факт о конструкции пути |
| `FROG_WING` 1.5 м — длина галочки поверх стрелки | **клиент** | штрих для читаемости, ничем не измеряется на месте |
| шаг тесселяции дуги 0.5 м | клиент | способ изображения, не факт |
| толщина нитки 2 экранных px | клиент | по определению экранная |
| точка крестовины | сервер | один канонический ответ на вопрос, где она |

### Чего этот контракт НЕ несёт

`RenderGeometry` несёт вертикаль только начальными `z` и `slope`
(`compile.go:68`), но не цепочку вертикального профиля. Значит контракт
нейтрален к представлению **только в плане**: восстановить `z(u)` по нему
нельзя. Ссылаться на будущий вид из кабины как на обоснование сегодняшней формы
поэтому неправомерно, и настоящая спека этого не делает. Вертикальный профиль в
контракте — отдельная задача с отдельным потребителем.

## 3. Ресурс типа путевой конструкции

Метры и радианы, как везде в формате.

```json
{
  "id": "TRACK_MAIN_1435",
  "gauge": 1.435,
  "sleeper": { "pitch": 0.6, "length": 2.5, "width": 0.28 },
  "ballast": { "half_width": 1.75 }
}
```

Семантика каждого числа задаётся явно, иначе два разработчика реализуют разное:

- `gauge` — **между внутренними рабочими гранями головок рельсов**. Условные
  линии схемы — **символические нитки** и ставятся на ±`gauge`/2; они не
  претендуют на совпадение с геометрическими осями физических головок.
  Расстояние между осями головок равно `gauge` плюс ширина головки, а ширина
  головки сознательно не заведена (потребителя нет). Трёхмерный ассет, когда
  появится, должен иметь якорь на внутренней рабочей грани — либо потребуется
  профиль рельса;
- `sleeper.length` — размер **поперёк** пути, `sleeper.width` — **вдоль**;
- `ballast.half_width` — по верху призмы.

### Платформа — не свойство типа пути

Первая редакция положила `platform.offset` и `platform.width` в тип пути. Это
неверная модель: платформа — самостоятельный путевой объект со своим ID и
спаном (`schema.go:84`, `map-format-design.md:351`), и на одном пути могут
стоять платформы разной ширины и с разным отступом. Тип рельсошпальной решётки
их не определяет.

Размеры уезжают на сам объект:

```json
{ "id": "ST_A_PLAT_2", "kind": "platform", "span": [...], "side": "right",
  "offset": 1.75, "width": 3.0 }
```

`offset` — от оси пути до ближней кромки, `width` — поперёк. Отдельный
`platform_type` заводится, только если появится повторное использование
профилей платформ; сегодня потребителя нет.

**Валидация ресурса обязательна на сервере**: все величины конечны и строго
положительны, `id` уникальны, ссылка на неизвестный тип — ошибка. Небрежность
здесь не косметическая: `resample_uniform` в клиенте зацикливается при
неположительном шаге (`geometry_math.gd:105`, `ClearAhead-a3o`).

**Не заводится сейчас** (§8): `ballast.shoulder_slope` — ни один клиент его не
читает, а без высоты призмы и определения отношения число формы не задаёт;
`sleeper.type` (дерево/бетон) — ни один клиент их не различает, ассетов нет.

### Где типы живут авторитетно

Определения типов, run'ы и умолчание живут **в файле карты**, новым блоком
`construction` рядом с `topology` и `geometry`. Не отдельным ресурсом и не в коде
сервера: они авторские данные, привязка к ревизии получается по построению, а
отдельный ресурс заново открыл бы проблему кэширования (ниже).

```json
"construction": {
  "default_type": "TRACK_MAIN_1435",
  "types": [ { "id": "TRACK_MAIN_1435", ... } ],
  "runs":  [ { "id": "RUN_17", ... } ]
}
```

Компилятор разрешает умолчание и встраивает результат в артефакт.

### Привязка к ревизии — решается здесь, а не в открытых вопросах

Тип **встроен в артефакт геометрии** и меняется только вместе с ревизией карты.

Иначе воспроизводится записанный в `hash.go` баг этажом выше: URL содержит
только карту и ревизию, ответ отдаётся с `Cache-Control: immutable` на год
(`geometry.go:73`), и правка независимо версионируемого типа изменила бы тело,
но клиент не пошёл бы перепроверять URL. Пара `(map_id, revision)` обязана
определять ровно один артефакт (`map-format-design.md:234`).

Список типов сортируется по `id` перед сериализацией: порядок обхода Go-map
недетерминирован, а хеш считается по отдаваемым байтам.

## 4. Три уровня: рецепт, особенности, исключения

Контракт не несёт ни полигонов, ни мешей: полигоны бесполезны трёхмерному виду,
меши — схеме. Но и отдавать двенадцать тысяч шпал ST_A отдельными инстансами
неразумно — `map-format-design.md:210` уже отделяет визуальные «мегабайты» в
отдельный ресурс именно поэтому.

**Уровень 1 — регулярное повторение: рецепт.** Шпалы, нитки, балласт вдоль
обычного пути.

**Уровень 2 — особенности устройств: канонические адреса и позы.** Там, где
важен один ответ на вопрос «где именно»: носок и крестовина стрелки, стык типов.
Форма задана в §5. Виды: `switch_toe`, `frog`, `type_seam`. `switch_heel` в
перечень не входит — сервер его не знает (§5).

**Уровень 3 — нерегулярные конструкции: отдельный рецепт устройства или
разреженные переопределения.** Стрелочные и крестовинные брусья переменной
длины, контррельсы, мостовые и переездные зоны, намеренно сдвинутые или
отсутствующие шпалы, импортированное фактическое расположение. **Заводится
только при появлении конкретного потребителя** — иначе рецепт обрастает
условными операторами и превращается в собственный язык генерации.

### Рецепт должен быть полным

Неполный рецепт хуже отсутствующего: он создаёт видимость согласия. Обязательны:

**`construction run` — авторитетный факт о физической решётке, материализуемый
авторингом.** Он независим от нарезки на `RenderElement`: элементы режутся ради
топологии и профиля, а не потому, что там начинается новая шпальная решётка.
Начинать фазу заново на каждом элементе нельзя — смена внутренней сегментации
карты переставила бы шпалы, хотя путь не менялся. Выводить run'ы из топологии
автоматически тоже нельзя: на развилке выбор продолжения неоднозначен.

```json
{
  "id": "RUN_17",
  "type": "TRACK_MAIN_1435",
  "coordinate": "u",
  "phase": 0.15,
  "spans": [
    {"element": "ST_A_E_T2", "from": 0,  "to": 100, "direction": "forward"},
    {"element": "ST_A_E_T3", "from": 20, "to": 80,  "direction": "reverse"}
  ]
}
```

Пишет их строитель, а не человек (§6) — авторинговая нагрузка ложится на
инструмент, и петля замыкается: процедурность на авторинге порождает и
устройства, и решётку.

- **Координата размещения — `u`**, не `s`. Выбор не оставляется разработчику:
  клиент не имеет цепочки вертикального профиля (§2) и восстановить размещение
  по `s` не способен.
- **Размещение считается в накопленной координате run `r`**, а не в локальном
  `u`: локальный `u` начинается заново на каждом элементе. Правило диапазона
  **полуоткрытое**: `phase + n × pitch ∈ [0, run_length)`. Так на стыке не
  возникает сдвоенной шпалы. Нынешний клиент всегда ставит шпалу в конечной
  точке (`geometry_math.gd:98`) — это будет исправлено. Особая шпала в конце,
  если понадобится физически, — переопределение уровня 3, а не исключение в
  общем алгоритме.
- **Позиция считается от аналитической `pose(u)`, не от тесселированной
  полилинии.** Тесселяция — клиентская деталь и на позиции влиять не должна;
  в рецепт она не входит. Иначе клиент, режущий дугу с шагом 0.5 м, и клиент,
  считающий аналитически, разойдутся при одинаковых `phase` и `pitch`.
- **Правило ориентации, заданное, а не упомянутое:** поперечная ось шпалы
  совпадает с левой нормалью аналитической `pose(u)`; якорь ассета — в
  геометрическом центре шпалы.
- **Версия алгоритма размещения** — часть артефакта, чтобы смена алгоритма не
  меняла молча старую ревизию.
- **Golden-векторы** на `pose(u)`, выбор станций и ориентацию.

### Покрытие, фаза и координата run

**Каждое ребро покрыто ровно одним run: без пропусков и без перекрытий.**
Проходы стрелок и глухих пересечений run'ами НЕ покрываются — их решётка
нерегулярна (стрелочные и крестовинные брусья), это уровень 3, и до появления
потребителя устройство рисуется собственным приближением клиента.

**Но исключение из регулярной решётки не означает исключения из типа.**
Устройство несёт **собственный `type`**, разрешаемый тем же правилом, что и у
run'а: опущен — применяется `construction.default_type`, в проводе ссылка всегда
явная. Без этого не определено, какую `gauge` сервер берёт для вычисления
крестовины (§5) и откуда приближение клиента берёт колею и балласт.

Совпадения типа устройства с типами примыкающих run'ов **не требуется**:
стрелка законно соединяет главный путь со станционным. Расхождение — не отказ, а
особенность `type_seam` на границе, которая в этой схеме уже есть.

Редакция 3 содержала здесь противоречие: тип назначался run'у, а умолчание —
элементам, не покрытым run'ом, у которых run'а нет по определению. Заводить им
неявный singleton-run нельзя: это вернуло бы привязку решётки к нарезке
элементов, ради ухода от которой run и заведён. Поэтому покрытие полное, а
**умолчание применяется к run'у с опущенным `type`**.

Накопленная координата run: `r ∈ [0, run_length)`, где `run_length` — сумма длин
спанов. Отображение `r` в локальный `u` внутри спана, начинающегося при
`r = r₀`:

```
forward:  u = from + (r − r₀)
reverse:  u = to   − (r − r₀)
```

`phase` нормализована: `0 ≤ phase < pitch`. Станции — `phase + n × pitch` при
`n ∈ ℤ≥0`, отбираются полуоткрытым правилом `∈ [0, run_length)`.

### Назначение типа

Тип назначается **`construction run`**, а не элементу и не проходу:

- умолчание объявлено в карте (§3) и разрешается **компилятором**, на сервере;
- в проводе у каждого run **всегда явный** идентификатор типа;
- клиент скрытого умолчания не применяет никогда;
- стык разных типов — граница run'ов и порождает особенность `type_seam`.

### Корневые поля провода

`DisallowUnknownFields` в `contract_test.go` делает имена частью контракта, а не
деталью реализации. `RenderGeometry` получает ровно четыре новых корневых поля:

| Поле | Что несёт |
|---|---|
| `track_types` | разрешённые определения типов, сортировка по `id` |
| `construction_runs` | run'ы с явным `type`, сортировка по `id` |
| `features` | особенности уровня 2, сортировка по `(owner, kind, addresses)` |
| `placement_algorithm` | версия алгоритма размещения |

На развилке одна фаза не может непрерывно продолжиться по обеим ветвям: там
начинается рецепт устройства либо объявленный `type_seam`.

### Критерий согласия рендереров

Не «одинаковая картинка» — она между видом сверху и видом из кабины невозможна
и не нужна. Критерий: **эквивалентность инженерной сцены** — совпадение
множества размещённых элементов, их канонических поз и размеров в пределах
объявленного допуска. Скругления, стыки, порядок слоёв и уровни детализации
остаются клиентскими и совпадать не обязаны.

### Идентичность процедурных элементов

Порядковый номер `n` **не является доменной идентичностью**: смена `origin`
перенумерует всё следующее. Контракт этого и не обещает. Когда появятся дефекты
пути, ремонт или фактически отсутствующая шпала, адресуемые исключения станут
объектами уровня 3, а не состоянием «шпалы №713».

## 5. Устройства

### Стрелка

Остаётся как есть: три порта, рукость, два адресуемых прохода, ресурс замыкания
(`RES_<id>`).

**Точка крестовины** отдаётся сервером как особенность уровня 2. Считать её
должен сервер: два клиента, независимо ищущие пересечение офсетных кривых, дадут
два разных ответа.

```json
{
  "owner": "ST_A_SW_1",
  "kind": "frog",
  "point": {"x": 333.14, "y": -1.84},
  "addresses": [
    {"element": "ST_A_SW_1:straight",  "u": 29.2, "tangent": {"x": 1.0,   "y": 0.0}},
    {"element": "ST_A_SW_1:diverging", "u": 29.3, "tangent": {"x": 0.994, "y": -0.110}}
  ]
}
```

Смысл полей задан точно, иначе форма двусмысленна:

- `addresses[i].u` — позиция на **осевой линии** соответствующего прохода;
- `point` — физическая точка крестовины, на пересечении **офсетных ниток**. Она
  **не совпадает** ни с одной из осевых поз, поэтому и передаётся отдельно;
- `tangent` относится к тому адресу, внутри которого записана, и направлен по
  ходу возрастания `u`. Единичный. Порядок адресов — прямой проход, затем
  боковой;
- одного `heading` у особенности нет и быть не может: направлений два.

Все поля — производные одного скомпилированного артефакта, поэтому дублирование
допустимо; сервер обязан строить их **одной функцией** и проверять
согласованность `point` с адресами.

#### Алгоритм: какие две нитки пересекать

Формы результата мало — без заданной функции два серверных разработчика дадут
разные канонические `point` и `u`, а контракт существует ровно чтобы этого не
было.

У стрелки четыре нитки: по две у каждого прохода, на ±`gauge`/2 от осевой,
где `gauge` берётся из **типа самого устройства** (§4), а не из типов
примыкающих путей.
Пересекаются **не любые две**. Нормали берутся левые (`geometry_math.gd`:
`normals` возвращает нормаль влево от движения), знак смещения — по ним:

```
hand = "right":  прямой проход −gauge/2  ×  боковой проход +gauge/2
hand = "left":   прямой проход +gauge/2  ×  боковой проход −gauge/2
```

Почему так: боковой путь уходит вправо (для правой стрелки), значит его **левая**
нитка идёт навстречу **правой** нитке прямого пути и пересекает её. Вторая пара
ниток расходится и не пересекается никогда.

Требования и отказы:

- пересечение обязано быть **ровно одно** в пределах `u` обоих проходов;
- ноль пересечений означает, что нитки не успевают сойтись внутри устройства —
  геометрия перевода неверна (например, радиус велик для длины прохода), это
  **отказ валидации**, а не «особенность отсутствует»;
- больше одного — тоже отказ: канонического ответа нет;
- касательное касание без пересечения — отказ.

Проверяемое следствие для `ST_A_SW_1` (`R = 300`, `gauge = 1.435`): нитки
сходятся, когда оси разошлись на колею, то есть при `R(1 − cos(s/R)) = 1.435` —
это `s ≈ 29.36 м` при длине бокового прохода `33.21 м`. Крестовина внутри
устройства; если реализация даст заметно другое число, она неверна.

**Конец остряка сервер вывести не может.** Первая редакция настоящей спеки
утверждала обратное — это ошибка. Он не следует из осевых линий и колеи: его
задаёт конструкция перевода (длина остряка, тангенциальная или секущая форма,
положение корня), а этих данных нет ни в карте, ни в типе пути. Возможны ровно
три честных исхода, и выбрать надо один:

1. конец остряка материализуется авторингом в карте;
2. он входит в **тип стрелочной конструкции** — новый ресурс, отдельный от типа
   пути;
3. контракт признаёт его **клиентской эвристикой** и не отдаёт вовсе.

До появления типа стрелочной конструкции действует (3): клиент рисует остряк
условно, и это записано в коде как временное (`turnout_layer.gd:18`).

Статическая геометрия и **положение** переведённой стрелки не смешиваются:
положение — состояние из потока, его сегодня не существует.

### Глухое пересечение — форма спроектирована, реализация под условием

Устройство нужно и в отраслевой модели первоклассно. Но по правилу §8 его
реализация **гейтится конкретным потребителем**, и критерий такой:

> Существует ли карта, модуль авторинга или импортируемый набор данных, который
> проект обязан принять и в котором пересечение требуется?

Тестовая фикстура, созданная ради самой формы, потребителем не считается.
Довод «валидатор делает пересечение невыразимым» отвергнут в ревью и снят: им
же можно потребовать немедленно завести перекрёстные съезды, мосты и переезды,
и правило перестанет фильтровать что-либо.

Спроектированная форма, когда потребитель появится:

- четыре порта, две явно заданные пары; два адресуемых прохода со стабильными
  ID — урок §8 про «дыру первой редакции» повторять не надо;
- перехода с прохода на проход нет; состояния нет;
- собственная геометрия обоих проходов; **ровно одно невырожденное поперечное
  пересечение**, иначе отказ валидации;
- **два `u` не хранятся в карте**: они вычисляются компилятором и живут в
  скомпилированном артефакте. Хранить их рядом с геометрией — завести второй
  источник истины, допуск согласования и устаревающие адреса при правке
  геометрии;
- совпадение `z` обоих проходов в точке, в допуске.

Новое объяснение в `intersect.go` должно быть **узким**: разрешается не
«пересечение рядом с объявленным устройством», а именно эта пара элементов,
именно вычисленная пара `u`, не касательно, без наложения, без второго
пересечения, с совпадением высот. Пересечения этих проходов с третьими
элементами остаются ошибками.

**Блокировочная часть не заводится сейчас**: `resource_id`, защитные спаны,
момент захвата и освобождения, семантика занятости. Замыкание маршрутов — веха
В2, его не существует, и заполненная форма без исполнителя окажется неверной. В
В2 блокировка сошлётся на стабильные ID проходов; менять сам crossing не
придётся.

## 6. Процедурность на авторинге — и почему

Человек не пишет руками геометрию устройства. Он показывает намерение («отсюда
ветка налево, марка 1/9»), строитель считает остальное по правилам и
**записывает результат в карту** с устойчивым ID.

Первая редакция обосновывала это отклонённым генератором и устойчивостью
идентификаторов. Оба довода в ревью признаны негодными и заменены:

- `deferred-decisions.md:144-176` отвергает генерацию **целых игровых станций**
  из-за отсутствия метрик качества. Детерминированного разворачивания
  объявленного устройства при загрузке он не запрещает и прямо разрешает
  модульную сборку;
- довод про идентичность бьёт только по схеме «нашли пересечение геометрии →
  решили, что это устройство → придумали ему ID». Он не бьёт по схеме «в карте
  объявлен `SW_17` → загрузчик детерминированно разворачивает его в
  `SW_17:straight` и `SW_17:diverging`»: производные ID зависят от родителя и
  роли, а не от координат.

**Настоящее основание — воспроизводимость ревизии** (`map-format-design.md:320`,
§7): никакой подгонки при загрузке, иначе результат зависит от версии решателя, а
пара `(map_id, revision)` обязана определять ровно один артефакт. Материализация
на авторинге даёт это по построению; генерация на загрузке — только при
сохранении старых версий алгоритма, что дороже.

Модель совпадает с записанной для импорта: импорт создаёт **кандидата**,
валидатор проверяет нормы, человек подтверждает.

## 7. Марка крестовины: откат ошибки

`ClearAhead-109` предписал сделать `frog` обязательной в валидации карты; это
сделано и **отменяется**. §8 объявляет марку необязательной сознательно:
«необязательная марка крестовины как **происхождение, а не ограничение**» — ради
импорта реальных станций с произвольными радиусами.

Первая редакция обосновала откат тем, что клиент построит крестовину «из угла и
радиуса примитива». Это неверно: у прямого примитива нет ни угла, ни радиуса;
проход может состоять из нескольких примитивов; угол крестовины — локальный угол
между нитками в точке пересечения, а не `angle` одной дуги; пересечений
офсетных кривых может быть несколько или ни одного.

Правильно:

- `frog` необязателен и в карте, и в проводе;
- на геометрию он **не влияет никогда**;
- присутствует — показывается как подпись;
- позиция и локальные касательные приходят особенностью уровня 2 (§5);
- подробная трёхмерная крестовина (желоба, усовик, носик, профиль) откладывается
  до появления потребителя.

Затронуты: `validate.go:218`, `compile.go:171`, `geometry_parser.gd:21`,
`turnout_layer.gd:104`.

## 8. Правило потребителя, применённое симметрично

Проект дважды применил правило «объявленная форма без потребителя окажется
неверной»: слоя диспетчерской схемы нет, клотоида отложена.

**Не заводим сейчас:** `ballast.shoulder_slope`; `sleeper.type` как выбор
ассета; масса, плотность и материал как расчётные величины; подробные профили
рельса, скрепления, физическая крестовина; блокировочная часть глухого
пересечения; уровень 3 (нерегулярные конструкции).

**Заводим сейчас, потому что потребитель уже есть:** ширина и отступ платформы
(клиент их уже потребляет, выдумывая); фаза и координата шага шпал; точная
семантика `gauge`, `length`, `width`, `half_width`; валидация ресурса типа;
привязка типа к ревизии и его участие в хеше.

**Заводим при подходе к вехе:**

| Величина | Потребитель | Веха |
|---|---|---|
| масса, длина, тормоза, сцепка подвижного состава | физика манёвров и ведения | В2–В3 |
| класс пути по осевой нагрузке, допустимая скорость | ограничения и разрешения | В2 |
| минимальный радиус, предельный уклон | валидация (`validation_profile`) | В3 (`ClearAhead-724`) |
| блокировка глухого пересечения | замыкание маршрутов | В2 |
| клотоида, возвышение, вертикальный профиль в контракте | вид из кабины, если состоится | не назначена |

## 9. Совместимость провода

`contract_test.go:14` декодирует ответ с `DisallowUnknownFields` **намеренно**:
лишнее поле роняет тест, а не доезжает до клиента незамеченным. Клиент на Godot,
наоборот, лишние поля игнорирует.

Из этой асимметрии следует: у провода **нет версии схемы**, а `map_revision` —
версия содержимого, не контракта. Поэтому добавление полей настоящей спеки —
**атомарное обновление обеих сторон и эталона в одном изменении**. Если позже
понадобится независимая эволюция сторон, потребуется версия провода; сейчас она
не заводится (потребителя нет).

## 10. Что меняется в коде

### Ревизия и версия формата — поднимаются, а не подменяются

`ST_A` сегодня на `map_revision: 2`, и тело `/revisions/2/geometry` уже отдано
как immutable. Добавление типов, run'ов, особенностей и размеров платформ это
тело изменит. Значит реализация **обязана поднять ST_A минимум до ревизии 3**;
обновить один эталон и ETag недостаточно — это и есть тот самый класс ошибки,
о котором предупреждает комментарий в `hash.go`.

Формат карты строгий: `FormatVersion = 1` (`limits.go:10`), а в шапке пакета
записано «всё неизвестное — отказ, согласования минорных версий нет». Новые поля
карты (run'ы, размеры платформ) старый читатель отвергнет. Поэтому
**`format_version` поднимается до 2**, единственная карта мигрируется. Оставить
новые поля под прежним номером означало бы, что две несовместимые формы
называются одной версией.

### Канонический порядок — у всех новых массивов

Порядок обхода Go-map недетерминирован, а хеш считается по отдаваемым байтам.
Сортируются: типы — по `id`; run'ы — по `id`; особенности — по
`(owner, kind, addresses)`; спаны внутри run — в авторском порядке прохождения
(он и есть смысл, сортировке не подлежит).

### Прочее

Сервер: ресурс типа и его валидация; встраивание типов в артефакт; рецепт
размещения с `construction run`; особенности уровня 2 (крестовина, стык типов);
размеры на путевых объектах; откат обязательности `frog`.

Клиент: константы `GAUGE_HALF`, `SLEEPER_STEP`, `SLEEPER_HALF`, `SLEEPER_WIDTH`,
`BALLAST_HALF_W`, `PLATFORM_OFFSET`, `PLATFORM_WIDTH` заменяются числами из типа;
`FROG_WING` остаётся клиентским как стиль; полуоткрытое правило последней шпалы;
крестовина из особенности, а не из марки; `resample_uniform` отвергает
неположительный шаг.

Эталон и хеш обновляются в том же изменении (§9).

## 11. Открытые вопросы

1. Конец остряка: авторинг, тип стрелочной конструкции или клиентская эвристика
   (§5). До решения действует эвристика — она не блокирует реализацию.
2. Нужен ли тип балласта отдельно от типа пути: главный и станционный путь
   различаются шпалой и балластом, но не колеёй. Не блокирует: сегодня тип один.
3. Глухое пересечение: есть ли конкретная карта, модуль авторинга или
   импортируемый набор, который проект обязан принять и в котором пересечение
   требуется (§5). **Решение владельца.** Не блокирует остальную реализацию.

Вопросы «область назначения типа» и «тип по умолчанию» из первой редакции
закрыты в §4: тип назначается run'у, умолчание разрешает компилятор, в проводе
ссылка всегда явная.
